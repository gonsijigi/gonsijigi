# 발표 Q&A 노트 — Git 브랜치 전략 관련

## 1. 사고 개요
- 무엇: risk_keywords state 통합 + admin AI 해석 컬럼 추가 작업 중,
  클로드 코드가 feat 브랜치를 파지 않고 main에 직접 커밋함.
- 언제: 7/7 밤
- 위반한 규칙: CLAUDE.md의 "main 직접 커밋 금지" 원칙
- 영향: 다행히 SMOKE 테스트 통과, 단일 종목 조회 시 위험 키워드 정상 표시까지
  확인되어 기능적 손실은 없었음. 다만 PR 리뷰 절차를 거치지 않고
  이력 관리 원칙이 깨진 것 자체가 문제.

## 2. 원인 분석
- 클로드 코드에게 작업을 지시할 때 "브랜치부터 파라"는 지시가
  매번 명시적으로 포함되지 않아, 모델이 편의상 현재 브랜치(main)에서
  바로 작업을 이어감.
- 사람이 커밋 직전에 브랜치를 재확인하는 절차가 없었음.

## 3. 재발 방지 조치
- 팀 운영 규칙에 다음을 영구 반영:
  "클로드 코드에게 새 작업을 지시하기 전에는 항상
   git branch --show-current 로 확인 → main이면
   git checkout -b feat/[작업명] 으로 새 브랜치부터 판다.
   한 줄짜리 수정이라도 예외 없음."
- 이후 진행된 PR #1(DART 매핑), PR #2(리플레이 모드),
  PR #3(HITL↔admin 큐 연결)는 모두 이 규칙을 지켜 브랜치→PR→머지
  절차로 정상 진행됨.

## 4. 발표 Q&A 예상 질문 대비

**Q. Git 브랜치 전략은 어떻게 가져가셨나요?**
A. feature 브랜치 전략을 기본으로 하되, 팀 초반 한 차례 main 직접
   커밋 사고가 있었습니다. 다행히 기능 테스트(SMOKE)까지 통과된
   상태라 서비스에 영향은 없었지만, 이후 "클로드 코드에게 작업
   지시 전 브랜치 확인을 의무화"하는 규칙을 CLAUDE.md에 명문화해
   재발을 막았습니다. 이후 3건의 PR은 모두 정상 절차를 따랐습니다.

**Q. AI 코딩 도구를 쓰면서 겪은 실수는 무엇이고 어떻게 대응했나요?**
A. AI 에이전트가 작업 맥락(브랜치 등 안전장치)을 사람이 명시하지
   않으면 생략할 수 있다는 걸 직접 경험했습니다. 그래서 이후로는
   "AI에게 반복적으로 요구되는 안전 절차는 매번 자연어로 설명하지
   않고, 프로젝트 규칙 문서(CLAUDE.md)에 고정해 AI가 매 세션마다
   자동으로 따르게" 만드는 방식으로 개선했습니다.

**Q. 왜 즉시 롤백하지 않았나요?**
A. 커밋 자체는 기능적으로 문제가 없었고(SMOKE 테스트 통과,
   기능 정상 동작 확인), 되돌릴 경우 오히려 정상 동작하는 기능을
   잃는 리스크가 있어 롤백 대신 "절차 개선"으로 대응하는 것이
   합리적이라 판단했습니다.
