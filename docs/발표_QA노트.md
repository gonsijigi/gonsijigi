# 발표 Q&A 노트 — Git 브랜치 전략 관련

## 1. 사고 개요
- 무엇: risk_keywords state 통합 + admin AI 해석 컬럼 추가 작업 중,
  클로드 코드가 feat 브랜치를 파지 않고 main에 직접 커밋함.
- 언제: 7/7 밤
- 위반한 규칙: CLAUDE.md의 "main 직접 커밋 금지" 원칙
- 영향: 다행히 SMOKE 테스트 통과, 단일 종목 조회 시 위험 키워드 정상 표시까지
  확인되어 기능적 손실은 없었음. 다만 PR 리뷰 절차를 거치지 않고
  이력 관리 원칙이 깨진 것 자체가 문제.

## 2. 원인 분석
- 클로드 코드에게 작업을 지시할 때 "브랜치부터 파라"는 지시가
  매번 명시적으로 포함되지 않아, 모델이 편의상 현재 브랜치(main)에서
  바로 작업을 이어감.
- 사람이 커밋 직전에 브랜치를 재확인하는 절차가 없었음.

## 3. 재발 방지 조치
- 팀 운영 규칙에 다음을 영구 반영:
  "클로드 코드에게 새 작업을 지시하기 전에는 항상
   git branch --show-current 로 확인 → main이면
   git checkout -b feat/[작업명] 으로 새 브랜치부터 판다.
   한 줄짜리 수정이라도 예외 없음."
- 이후 진행된 PR #1(DART 매핑), PR #2(리플레이 모드),
  PR #3(HITL↔admin 큐 연결)는 모두 이 규칙을 지켜 브랜치→PR→머지
  절차로 정상 진행됨.

## 4. 발표 Q&A 예상 질문 대비

**Q. Git 브랜치 전략은 어떻게 가져가셨나요?**
A. feature 브랜치 전략을 기본으로 하되, 팀 초반 한 차례 main 직접
   커밋 사고가 있었습니다. 다행히 기능 테스트(SMOKE)까지 통과된
   상태라 서비스에 영향은 없었지만, 이후 "클로드 코드에게 작업
   지시 전 브랜치 확인을 의무화"하는 규칙을 CLAUDE.md에 명문화해
   재발을 막았습니다. 이후 3건의 PR은 모두 정상 절차를 따랐습니다.

**Q. AI 코딩 도구를 쓰면서 겪은 실수는 무엇이고 어떻게 대응했나요?**
A. AI 에이전트가 작업 맥락(브랜치 등 안전장치)을 사람이 명시하지
   않으면 생략할 수 있다는 걸 직접 경험했습니다. 그래서 이후로는
   "AI에게 반복적으로 요구되는 안전 절차는 매번 자연어로 설명하지
   않고, 프로젝트 규칙 문서(CLAUDE.md)에 고정해 AI가 매 세션마다
   자동으로 따르게" 만드는 방식으로 개선했습니다.

**Q. 왜 즉시 롤백하지 않았나요?**
A. 커밋 자체는 기능적으로 문제가 없었고(SMOKE 테스트 통과,
   기능 정상 동작 확인), 되돌릴 경우 오히려 정상 동작하는 기능을
   잃는 리스크가 있어 롤백 대신 "절차 개선"으로 대응하는 것이
   합리적이라 판단했습니다.

## 5. 기능 관련 예상 Q&A (PR별 누적)

**Q. 에이전트가 '판단'하는 지점을 코드에서 어떻게 찾나? (PR: 주석 대공사)**
A. 세 가지 태그로 전부 추적됩니다 — [ORCHESTRATION](에이전트의 판단·분기,
   '생각→행동' 순서로 서술해 ReAct 흐름이 주석만으로 드러남),
   [SAFETY](가드레일·HITL·마스킹·스포트라이팅·출처 강제),
   [COST](토큰·외부호출 절약 지점). 예: grep -rn "\[ORCHESTRATION\]" app/
   README의 오케스트레이션 표가 이 태그들과 1:1로 대응합니다.

**Q. 채점(리뷰) 환경에서 데모를 직접 돌리기 어려우면 어떻게 확인하나? (PR: 제출 산출물)**
A. docs/demo/ 에 실제 구동 영상 2편을 포함했습니다 —
   ① 풀데모(리플레이·실제 공시 데이터): 관심종목 등록 → 5종 선별 알림([수주] 직행,
      유상증자는 검토 큐) → HITL 승인 → 알림 도착·자금목적 라벨 → 가드레일 거절
   ② 라이브(실제 DART·LLM): "최근 SK하이닉스 공시" 해석(로딩 팝업 포함) →
      "살까말까?" 즉시 거절. 직접 실행 절차는 docs/실행가이드.md 참고.

**Q. 머지 충돌로 코드가 중복·꼬이면 어떻게 감지하고 처리하나? (PR: interpret 중복 정의 제거)**
A. 실제로 겪었습니다 — 오래된 브랜치의 충돌을 '양쪽 유지'로 해소하면서
   interpret.py에 구버전 클래스·함수가 통째로 중복 삽입됐고(+41/-0 순추가가 단서),
   파이썬은 나중 정의가 이겨서 개선된 프롬프트 설정이 조용히 무효화됐습니다.
   감지: main 동기화 직후 파일 이상 여부 확인 + 정의 중복 전수 스캔
   (grep으로 def/class 중복 검사). 처리: 원인 커밋을 git log -p로 특정하고,
   이미 리뷰·머지된 의도(신버전)만 남기는 최소 수정 PR로 복원했습니다.
   교훈: 머지 후 스모크 통과만으로는 '조용한 덮어쓰기'를 못 잡는다 —
   그래서 중복 정의 스캔을 제출 전 점검 목록에 추가했습니다.

**Q. '필수 5종' 선별 알림의 기준 근거는? (PR: 5종 선별 알림)**
A. 유가증권시장 공시 유형을 투자자 영향 기준으로 분석해
   수주(매출 5%↑ 계약만 공시) · 유상증자(즉시 희석, 자금 목적이
   시설투자냐 채무상환이냐로 해석이 갈림) · 전환사채(잠재 희석·리픽싱) ·
   내부자 매매(경영진의 실제 판단 신호) · 실적(선반영)을 추렸습니다.
   근거 정리는 docs/공시_도메인_한장.md §2. 유상증자는 원문에서
   자금 사용목적을 읽어 라벨까지 자동 표기하되, '호재/악재' 단정은
   가드레일 원칙에 따라 하지 않습니다("~로 해석되는 경우가 많음"까지만).
